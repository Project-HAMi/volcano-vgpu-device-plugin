# Allocation integration validation

This document accompanies cross-component tests for the proposed HAMi alignment changes. It describes candidate behavior, not features already present in upstream main.

## Dependencies

The tests in `pkg/plugin/allocate_integration_test.go` require the allocation-validation test fixture, plugin-owned cache manager, and MIG backend abstraction from the related implementation PRs. They are intentionally a separate draft change. On unmodified main, `go test ./pkg/plugin` cannot compile these tests because those prerequisites are absent. An image build that does not compile tests is not evidence that this test suite passes.

After applying the prerequisites:

```sh
go test -race ./pkg/plugin -run TestIntegratedAllocate -count=1
```

The tests check that cache preparation or MIG export failures do not consume allocation annotations, and that retrying allocation retains the cache filename and contents. They use fake Pod operations and a fake MIG backend. They do not validate how kubelet requests are associated with a Pod.

## Previously tested combined candidate

The original combined candidate was `c0faed1a05739ae67b4dfd2f8186779e90a80adf`, based on `6063efe9806ee7bd2fd966fc65f155c65c95696b`. Subsequent rebasing and dependency updates do not imply a new cluster run.

| Environment / case | Observed result |
| --- | --- |
| K3s v1.32.5, Mokka v0.4.0, two simulated T4 GPUs, unmodified Volcano v1.15.1 | Single-container allocation ran; the first Allocate for a two-GPU-container Pod failed: request count 1 versus annotation count 2. |
| K3s v1.34.3, Fake GPU Operator v0.2.0 stock mock, eight 40 GiB A100s, unmodified Volcano v1.15.1 | Single-container allocation, returned environment/device nodes, and sequential capacity release/rescheduling were observed. |
| FGO, confirmed `deviceshare.NodeLockEnable: true` | Both baseline and combined candidate ran eight concurrent single-container Pods. Both still failed the two-container case. This is a finite sample, not proof of all concurrent timings. |
| Configuration-transition first run | No node-lock acquisition was observed and eight Pods failed. Cause remains unresolved; excluded from the effective-lock sample. |

FGO used `gpuMemoryFactor=8`: a 1000-unit request resulted in 8000 MiB in the Allocate environment. Driver-library mounts, mock environment variables, and DeviceSpec settings were applied to the isolated test deployment. Plugin health checking was disabled for this FGO run. It was not a pure Helm-values deployment.

Mokka's Xid simulation uses a shared one-shot event source: different plugin watchers consumed the event in different runs. The same behavior was observed on the original baseline. The monitor cache evidence used a C fixture; it was not generated by a CUDA workload.

These results do not validate real CUDA execution, hardware isolation, MIG instance behavior, or GPU workload continuity. The multi-container identity limitation is still unresolved. Keep the mock observations separate from unit tests and real-hardware acceptance.
